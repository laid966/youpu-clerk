# 15 · 扩展与落地：我们这个 agent 怎么长大

> 你问：怎么像蚂蚁阿福那样扩展？我们有潜力吗？怎么把空缺留出来？
>
> 这份文档回答这三件事。**先说一个必须掰开的前提，否则方向会跑偏。**

---

## 一、我们和阿福不是一类东西

| | 蚂蚁阿福 | **auditkit（我们）** |
|---|---|---|
| 是什么 | 面向 C 端的 **AI 健康助手**（生成器） | 面对 **AI 输出** 的**审计器**（质检层） |
| 产出 | 回答、解读、导诊 | **"这份 AI 输出哪里错了"** 的清单 |
| 规模怎么算 | 用户量（月活） | **接入的场景数 × 被审计的产物量** |
| 谁付费 | C 端 / 平台 | **下游用 AI 做判定的机构**（它们怕出错） |
| 出错代价 | 用户看错 | 机构**放行了一份错误判定** |

**结论：我们不该、也不可能"做成另一个阿福"。**
阿福的护城河是流量和生态，那是烧钱的事。

**我们的护城河只有一个：证明"判定类 AI 的输出是可验证的"。**
一旦这件事成立，我们就是**所有判定类 AI 的质检层**——体检解读、信贷审批理由、
理赔说明、录取决定、风控结论，**全都需要它，而且全都没有现成的解法。**

> 这就是"稀缺"的真正来源：**不是某个功能没人做过，而是"验证方法本身"没人做扎实。**

---

## 一·补、必须说清的前人位置

> **下面那套"内核 + 插件"的做法不是我们发明的，是成熟模式。**
> 完整的对照表、诚实的"非创新清单"、以及可用的面试话术，见
> **[16-优势与创新点.md](16-优势与创新点.md)**。

一句话先说在这儿：

- 内核 + 插件分离 = **Microkernel / Plugin Architecture**（软件架构教科书里的模式）
- 独立 oracle 交叉验证 = **Differential Testing / N-Version Programming**（航电容错的经典手段）
- 故意注入缺陷来量召回 = **Fault Injection**（可靠性工程常规做法）
- 改坏代码看测试抓不抓 = **Mutation Testing**（1970 年代就有）

**每一个部件都有成熟前人，一行都不是我们首创**——而且 2026 年这个方向正在被填
（已经出现 N-Version Programming with Coding Agents、SmartOracle 这类工作）。

**我们的贡献在「闭环 + 证据 + 承认边界」，不在架构首创。**
面试时按这个口径讲才站得住；讲成"我发明了一个新架构"会被一次追问拆穿。

---

## 二、有潜力吗？有，但潜力在三个维度上

| 维度 | 现在 | 天花板 | 瓶颈在哪 |
|---|---|---|---|
| **场景数**（横向） | 1 个体检场景 | 判定类场景**理论上无限** | 每个场景要有一份规则集 + 一份知识库 |
| **检查器数**（纵深） | 6 个确定性 + 1 个语义 | 按场景可插拔 | **原来必须改核心代码** ← 已修 |
| **准确性**（复利） | 召回 95.0%（60 条基准） | 靠"人工复核回流"持续上升 | 回流通道**还没有** |

**这三个维度里，第一个靠数据，第二个靠架构，第三个靠闭环。**

下面逐个说，并明确标注**哪里已经留了接缝、哪里还是空缺**。

---

## 三、五个扩展接缝：状态与做法

### 接缝 1：检查器 —— ✅ **已留出（本轮实现）**

**问题**：第一版 `detect()` 是一个大函数，6 个检查器的逻辑全内联在同一个 for 循环里，
共享局部变量。**想加第 7 个检查器必须改核心文件**，而且
`DETECTOR_TO_KINDS` 还要手工维护第二份。

**现在**：`audit/registry.py` + `audit/detect.py` 重构成注册表。

```python
from audit.detect import Finding, register_detector
from audit.registry import DetectorSpec

def 利率口径检查(ctx):
    for item, metric in ctx.items():
        if 条件(item, metric):
            yield Finding(detector="rate_basis", target=item.code, ...)

register_detector(DetectorSpec(
    name="rate_basis",
    kinds=("wrong_rate_basis",),
    run=利率口径检查,
    description="防的是：把日利率写成月利率这类口径错误",
    requires_report_values=True,
))
```

注册之后 `detect()` 自动带上它，**核心调度代码一行都不用改**。
`tests/test_registry.py` 里真的注册了一个新检查器来证明这件事。

**顺手还修了一个隐患**：`DETECTORS` 是导入时的**快照**，不是活清单。
拿"现在有哪些检查器"要用 `detector_names()`。这条差异写进了测试和注释——
**静态清单和活清单混用，是插件系统最经典的坑。**

**每个检查器还要标注两件事**（写在 `DetectorSpec` 里，不写就报错）：

- `kinds`：它负责哪些缺陷类型——**评测配对要用**，也是"检查器清单"的唯一事实来源
- `requires_report_values`：它是否需要原始数据——**这是差分审计和普通"事实核查"的分界线**

### 接缝 2：缺陷注入器 —— ⚠️ **有形状，未开放**

`audit/inject.py` 里已经有一个 `_INJECTORS` 字典（缺陷类型 → 注入函数），
形状就是注册表，但**没有对外暴露**。

**要留的空缺**：`register_injector(kind, label, fn, expected_detector)`。
这样新场景（比如信贷）能自己定义"利率口径写错"这种缺陷，而不用改注入器本体。

**为什么这一步很关键**：注入器决定了"标准答案从哪来"。
没有它，新场景就没有基准；没有基准，就**无法声称任何准确性数字**。

### 接缝 3：产物适配器 —— ❌ **空缺（最大的一个）**

现在被审计的产物形状是**体检专用的**：

```python
ArtifactItem(code, name, value, unit, reference_text, severity, explanation, advice, citations)
```

其中 `value / unit / reference_text` 是体检专有字段。信贷审批的产物没有"参考区间"。

**要留的空缺**：一个**适配器接口**，把任意判定类产物映射成统一形状：

```python
class ArtifactAdapter(Protocol):
    def to_artifact(self, raw: Mapping) -> Artifact: ...
    def required_context(self) -> tuple[str, ...]: ...   # 需要哪些源数据（用于差分）
```

**通用部分其实已经存在**：`severity`（判定结果）+ `explanation`（给用户看的说法）+
`citations`（依据）——**任何判定类 AI 的输出都有这三样。**
体检特有的只是 `value/unit/reference_text`。所以适配器是可行的，不是重写。

### 接缝 4：场景包 —— ❌ **空缺（部署必需）**

现在"一个场景"散落在四五处硬编码路径里：

```
domain/**.yaml            ← 规则
domain/med-metrics.yaml   ← 指标清单
rag/knowledge/*.yaml      ← 知识库
audit/detect.py           ← 检查器（原来是硬编码）
agent/prompts.py          ← 提示词
agent/policy.py           ← 策略
```

**部署时要能回答**："我们上线了哪些场景？各自用的是哪版规则、哪版提示词、哪版策略？"
现在答不出来——因为**没有清单**。

**要留的空缺**：`scenarios/<name>/pack.yaml`：

```yaml
name: med-checkup
domain_glob: domain/med-*/domain.yaml
metrics: domain/med-metrics.yaml
knowledge: [rag/knowledge/metric_notes.yaml, rag/knowledge/guideline_notes.yaml]
detectors: [oracle_differential, value_consistency, unit_consistency,
            citation_existence, advice_contract, safety_terms]
prompt_version: v2
policy: default
```

**好处**：加一个场景 = 加一个目录，不改代码。
而且这个清单**本身就是灰度与回滚的抓手**（"把 med-checkup 的 prompt 从 v2 回滚到 v1"）。

### 接缝 5：人工复核回流 —— ❌ **空缺（准确性复利的唯一来源）**

这是**提高准确性最重要的一条**，因为它是**唯一会自己长大的机制**：

```
线上审计 → 报出 12 条 → 人工确认：9 条真、3 条误报
                        ↓
          真阳 → 补进注入基准（作为新的缺陷类型/说法）
          误报 → 补进高难度负例（这才是误报率真正的考验）
                        ↓
                  重跑基准 → 数字更硬 → 提示词/检查器有的放矢
```

**现在 `human_review` 节点只是设了个标记**（`agent/nodes.py`），没有回流通道。

**要留的空缺**：一个 `feedback` 接口，把人工判定写回 `eval/`。
**注意红线**：回流的是**判定结果与文本类型**，不是真实用户数据。

## 四、分阶段路线（每阶段有门槛，不能跳）

| 阶段 | 目标 | **进入下一阶段的门槛** |
|---|---|---|
| **P0 单场景跑通**（现在） | 体检场景：规则 + 基准 + 审计图 + 网页 | ✅ 已达成：召回 95.0%、误报 ≤4.9% |
| **P1 可插拔** | 检查器/注入器/适配器都能注册 | 检查器 ✅；注入器与适配器 ❌ |
| **P2 第二场景** | **换一个完全不同的场景**（信贷审批理由）跑通 | 第二场景的召回与误报**有数字**——这一步才真正证明"可扩展" |
| **P3 多场景运营** | 场景清单 + 版本灰度 + 预算与限流 | 能回答"线上跑着哪些场景、各用哪版、成本多少" |
| **P4 准确性复利** | 人工回流 → 基准自动扩容 | **基准条数随运营时间增长**（不是靠手写） |

> **P2 是整个路线里最危险的一步。** 很多项目死在"只有一个场景能跑"——
> 因为那个场景的每一处都渗透着体检的假设。
> **能不能加第二个场景、且不用改核心代码，是"有没有扩展性"的唯一检验。**

## 五、"规模部署"真正卡在哪（说几句实话）

规模化最容易想错的是"成本"。其实成本不是瓶颈：

| 看起来的瓶颈 | 真实情况 |
|---|---|
| 模型调用贵 | 60 条基准约 ¥0.06；缓存之后重跑免费。**不是瓶颈** |
| 推理慢 | 确定性层不花钱不联网；只有一层用模型。**不是瓶颈** |
| **每个场景要有标准答案** | ⚠️ **这才是真瓶颈**。没有标准答案，就无法声称准确性 |
| **每个场景要有规则与知识** | ⚠️ 真瓶颈。这是**人工成本**，不是算力成本 |
| **漏报的代价无法量化** | ⚠️ 真瓶颈。决定"召回目标该定多高"的那个数，靠业务方给 |

**所以"大规模部署"的真实路径是：把"造标准答案"这件事的边际成本压下去。**
注入式基准就是干这个的——`audit/synth.py` + `audit/inject.py` 已经做到了
"**给定规则集，自动产出一份带标准答案的基准**"。

**这正是我们项目最有复用价值的部分。** 别人在做"更聪明的模型"，
我们在做"**能证明模型对不对的尺子**"——而尺子的复用性远高于某个模型。

---

## 六、诚实的边界：我们做不了什么

- ❌ **不能替代医生/信贷员做判定**。我们只审计"AI 的说法有没有越界、判定对不对"，
  判定本身仍由**规则 + 人**负责。
- ❌ **不能在没有规则集的场景落地**。没有规则就没有 oracle，就没有差分审计——
  只能退化成"事实核查"（而那个领域已有成熟工具，我们没有优势）。
- ❌ **不能靠模型自证**。同一模型自查 = 自己批改自己的卷子。
  这条是整个项目的立身之本，任何"省掉 oracle"的方案都是在拆地基。
- ❌ **不能直接上真实数据**。示例全是合成的；接真实数据要先解决脱敏与合规。

---

## 七、如果只做一件事

**做接缝 3（产物适配器）+ 接缝 4（场景包），然后加第二个场景。**

因为：

- 检查器注册表已经证明"架构上能插"
- 但**只有跑通第二个场景，才能证明那些假设真的没写死**（P2 的门槛）
- 而第二个场景一旦跑通，**你手里就有了"跨场景可扩展"的证据**——
  这是简历和面试里最硬的一句话，比任何指标都有说服力

**具体下一步**：选一个非医学的判定场景（**信贷审批理由**最合适：字段结构完全不同，
但同样有"判定 + 说法 + 依据"三件套），
按 `scenarios/<name>/pack.yaml` 的形式接入，**不允许改核心代码**。
如果逼得你必须改核心代码，那就是接缝没留对——**那个地方才是真正的空缺。**
