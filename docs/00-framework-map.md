# 00 · 框架地图、能力要求，以及"为什么这里必须用 Agent"

> 这是本项目的**总纲**。它不写业务，只回答三个问题：
> 1. 那些框架到底是什么，我该用哪个？
> 2. 为什么这件事不能直接用网页版聊天工具解决？
> 3. 做这行的人需要什么能力，这个项目能替我练到哪几条？
>
> 阅读顺序建议：先读第 4 节（为什么必须用 Agent），再回头读第 1、2 节。

---

## 1. 小白词典

| 名词 | 一句白话 | 在本项目里的角色 |
|---|---|---|
| 大模型 / LLM | 很会说话的程序，但不会算数，会一本正经地说错 | 只在"入口"和"出口"出现 |
| 提示词 / Prompt | 你对模型说的那段话 | 你要反复打磨的东西 |
| 结构化输出 | 让模型按固定表格格式回答，而不是写散文 | 保证模型吐出的东西程序能直接用 |
| 工具调用 / Tool calling | 让模型"去点一个按钮"，由程序真正执行 | 模型点"算钱"这个按钮，而不是自己猜 |
| LangChain | 一箱现成零件（连模型、接工具、管格式） | 当零件用，不当架构用 |
| **LangGraph** | 把流程画成一张流程图来执行；支持中途暂停、人工确认、断点续跑 | 项目主线 |
| Deep Agents | LangGraph 之上的"开箱即用大礼包"（自带规划、文件操作、子代理） | 降级为对照实验，不做主线 |
| Coze / Dify | 网页上拖拖拉拉就能搭机器人的平台 | 快速验证需求可以，做主力项目不行（不好测试、逻辑藏在平台里） |
| 存档 / checkpoint | 记住聊到哪了，崩了能续上 | 多轮追问与人工确认要用 |
| 人工确认 / interrupt | 算到关键一步先停下来问人"要不要这么做" | 本项目用它做"转人工复核" |
| 评测集 / 金标准 | 事先准备一批题 + 标准答案，每次改完代码重跑 | 证明改完没变差 |
| 基线对照 | 改之前存档一次，改之后对比 | **招聘方说是及格线，不是加分项** |
| CI（持续集成） | 代码一提交，机器自动跑测试，不通过不许合并 | 防止自己改坏 |
| 流式输出 / SSE | 回答一个字一个字往外蹦，像打字 | 演示体验 |
| MCP | 让模型接外部工具的一套通用协议 | 后续加分项，本期不做 |
| 可观测性 / trace | 每一步调了什么、花了多久、花了多少钱，全程留痕 | 判定类业务必须有 |
| AHT | 平均处理时长（客服行业核心指标） | 业务侧收益就靠它算 |

## 2. 框架地图：到底该用什么

| 名字 | 它是什么 | 强在哪 | 弱在哪 | 本项目怎么用 |
|---|---|---|---|---|
| LangChain | 组件库 | 连模型、工具、格式转换都有现成的 | 只给零件，不给流程控制 | ✅ 当零件 |
| **LangGraph** | 编排框架 | 显式流程、可暂停、可恢复、可审计 | 有学习成本 | ✅ **主线** |
| Deep Agents | 高级封装 | 开箱即用，适合长任务/研究型 | 逻辑不透明、不好精确测试 | ⚠️ 只作对照实验 |
| Coze / Dify | 低代码平台 | 半天能出原型，适合跟业务方对齐需求 | 逻辑藏在平台里、难做自动化评测、难嵌进企业系统 | ⚠️ 本期不用（后续可做原型对照） |
| LangSmith | 追踪与评测平台 | 开箱即用的可观测与评测 | 要花钱、数据出境 | ❌ 自建评测脚本代替 |
| OpenAI Agents SDK / Claude Agent SDK | 厂商官方框架 | 跟自家模型配合好 | 绑定厂商 | ❌ 不引入 |
| MCP | 工具接入协议 | 已成事实标准 | 本期非必需 | ⭕ 加分项 |

**本项目结论**：`Python + LangGraph（流程）+ LangChain 组件（零件）+ 模型 API（入口出口）+ 自建确定性引擎（算数）+ 自建评测脚本（证明）`。

> 记住一句话：**框架是交通工具，不是目的地。** 面试官扣分的是"只说自己精通 LangChain/LangGraph，但讲不清数据和评测"。

## 4. 为什么这里必须用 Agent（不能只用网页版聊天）

**一句话**：聊天机器人的产出是"一段听起来对的话"；Agent 的产出是"一件被办完的、有据可查的、错了能兜住的事"。

### 4.1 具体差在哪

以"这张票能不能退、退多少钱"为例：

| | 网页版聊天 | 判定 Agent |
|---|---|---|
| 算钱 | 模型"写"一个数字出来，可能对可能错，**而你无法验证** | 程序算，模型完全不碰算术 |
| 你的规则与数据 | 看不到你公司的票规，看不到订单 | 取相关条款 + 读订单数据 |
| 动作 | 只能输出文字 | 能查订单、锁座、发起退款、建工单、写日志 |
| 一致性 | 同一张票问两次，答案可能不一样 | 同样的事实永远得到同一个判定 |
| 留痕 | 聊天记录不是审计日志 | 结论可追溯到具体条款，可审计 |
| 成本与延迟 | 每次把几十页规则塞进上下文，又贵又慢 | 只取相关条款、可缓存、简单案例干脆不调模型 |
| 兜底 | 没有"转人工"这回事 | 拿不准或金额超限，自动转人 |
| 数据合规 | 把客户订单贴进公网聊天框 | 私有调用，数据不出域 |

### 4.2 你自己能做的验证（3 分钟，结论写进 `docs/03-failure-modes.md`）

1. 找一条稍微绕的规则，例如："退票费率按离站时间分档，且与舱位折扣叠加；联程票已使用一段的按比例折算。"
2. 把规则和一张具体订单一起粘给网页版聊天，让它算金额。
3. **同一个问题问三次**，记录三件事：
   - 三次答案是否完全一致
   - 它有没有说明自己引用了哪条规则
   - 你能不能自己核验它的算术过程

大概率你会看到至少一次不一致或算错。**那一刻你就明白企业为什么不敢把它直接接进生产流程。**

### 4.3 公平地说：什么时候网页版就够了

如果需求只是"讲讲退改签政策大概怎么回事""帮我写个话术初稿"——网页版完全够用，这时候做 Agent 就是**过度设计**。

Agent 的价值只在同时要满足这几件事的地方出现：

> **要准**（金额不能错）、**要留痕**（能审计）、**要接系统**（得真的办事）、**要控成本**、**要能兜底**。

判定类业务天生把这五条全占了。

### 4.4 关键区分：不是能力问题，是形态问题

现在的网页版已经带联网、代码执行等工具，"能不能算"这件事正在被补上。企业要的是：**接我的系统、按我的规则、可审计、能兜底、成本可控、数据不出域。** 这不是模型聪明程度的问题，是产品形态的问题——一个开放聊天窗口，天生嵌不进业务流程。

**选项目时的判据**：**如果一个项目网页版就能替代，那它就只是个 demo。**

## 5. 招聘市场调研结论（2026）

> 本节为外部调研整理，共 14 个来源（见 5.5）。发布开源版时可整节删除或移到内部笔记。

### 5.1 Agent 开发岗：真实考察项

筛选分四层：**基础功 → 评估闭环 → 工程深度 → 前沿视野**。其中「评估闭环」这一层淘汰掉约 **80%** 只"跑通 demo"的人（S3）。

- **检索类要报数**：Hit@5 < 0.7 就要回头怀疑切分与向量化；生成质量与检索质量分开看（S3）
- **任何优化必须有基线对照**："无基线 = 没做"；主动讲失败案例比讲成功更有说服力（S2、S3）
- **上下文工程**：窗口预算分配、历史滚动摘要、旧工具结果降级、子代理隔离（S3、S10）
- **工具层健壮性**：非法参数怎么处理、schema 校验、超时与退避、失败分类与降级、写操作串行（S5、S7、S10）
- **可靠性**：防死循环（最大步数 + 动作哈希）、目标漂移检测、每轮可回滚（S5、S10）
- **成本治理**：步数 / token / 墙钟 / 调用数 **四重硬上限**、缓存、模型分级路由（S5、S10）
- **可观测与评测**被列为与主循环同等重要：端到端 trace、失败归因、评测 harness、**CI 回归门禁**（S10）
- **MCP 是具体考点**：多 Server、能力协商、断线重连、工具动态摘除、工具投毒防范（S5、S10）
- **交付标准变了**：从"能跑"变成"**有数据证明它稳定地跑**"（S10）
- **Multi-Agent 判据**：只有需要并行广度或上下文隔离才拆；图结构编排优于自由群聊（S3）

### 5.2 加分项目 vs 减分项目

**加分**
- 真实场景、有真实用户（哪怕几十个）、有可量化收益闭环（S3、S4）
- 有基线对照的评估数字：检索命中率、工具调用成功率、P95 延迟、单次成本（S6、S9）
- 在 1–2 个模块上钻透：既有自适应路由/幻觉拦截，又有降级策略（S2）
- 有失败样本 + 归因 + 复测结果；能讲出取舍（为稳定性删链路、为成本缩上下文）（S1、S2）
- 有公开代码链接、demo 可点开、有开源贡献记录（S4）

**减分**
- 不给代码链接；明显的教程/培训班项目、看不出个人贡献（S4）
- 只堆名词与功能列表，一问设计就卡壳（S2）
- **场景同质化：智能客服、知识库问答、文档助手**；基础 RAG 与 LoRA 微调已属默认能力（S2）
- 只有成功截图；做成"什么都能做一点"的万能助手（S1）
- **只有功能没有评测；"准确率提升 15%"来自 20 条自测数据、无基线**（S1、S2）
- 过度强调"精通 LangChain/LangGraph"而缺基础功底（S4）
- 指标很美但用户为零的"面试型项目"（S3）

### 5.3 AI 产品经理岗：能力要求

- **五维**：技术认知、产品基本功、**数据与评估**、商业判断、伦理合规。其中「数据与评估」是区别于传统 PM 的核心硬技能（S8）
- **及格线**：理解"没有评测集就没有迭代"；检索准确率与生成质量分开看；读懂准确率/召回率/首字延迟（S8）
- **优秀线**：从零搭评测集（用例来源、标准答案、人工 vs 自动评分）；badcase 收集→归因→分发→验证的闭环；能识别"模型指标好但业务指标没动"（S8）
- 「熟悉大模型」三档自测：**L1 概念可用 / L2 方案可判 / L3 选型可辩**（S8）
- **商业判断**：token 边际成本、效果/成本/延迟的取舍、缓存与小模型路由、参与定价（S8）
- **面试考"怎么测"**：先定失败模式再定指标；每个指标必须给出测量方法（S11）
- 面试官常问：**拆解你亲手做的 AI 工作流，重点讲最意外的失败，以及后来怎么改设计**（S1）

### 5.4 开源项目如何真的被采用

- **上线即公开，不等 v1.0**："early but promising" 就可以发（S12）
- README 要有：动图 demo、徽章、贡献者区块、清晰的快速开始（S12）
- 找 **1k–10k star 仓库的维护者**（micro-KOL）而不是百万粉账号；20 个开发者可以撬动很大传播（S12）
- **持续被提及 > 一次性发布**：提交到 awesome-list（先开 issue 再提 PR，通过率高 2–3 倍）、newsletter 投稿、文档即 SEO、changelog 即博客（S12、S13）
- Issue 24 小时内首次响应；把支持问答沉淀成公开 Q&A（S13）
- 度量别只看 star：fork、依赖、文档流量、社区增长（S12）
- **反面提醒**：HN 上反复出现"建筑能力与获取注意力的能力几乎不相交""多数发布以死寂收场"（S14）——所以本项目把"真实用户"的优先级排在"star"之前

### 6.3 三档自测（来自 S8）

- **L1 概念可用**：能解释上面的小白词典
- **L2 方案可判**：给定场景能判断该用 RAG 还是判定引擎、该不该上 Agent
- **L3 选型可辩**：能说出为什么不用另一个方案，并给出取舍与代价

目标：本项目做完后，第 4 节能讲到 **L3**。

## 7. 本项目对照打勾（做完一项勾一项）

- [ ] 场景是有真实对错的判定类业务，不是又一个问答机器人（避开减分项）
- [ ] 算钱与判资格由程序完成，模型不碰算术
- [ ] 有自动生成的大规模评测集（1000 条）而不是手写 20 条
- [ ] 有基线对照，且评测分数下降会阻断合并
- [ ] 有转人工兜底与阈值，且能被测试验证
- [ ] 有失败模式文档（含 1 条主动砍掉的功能）
- [ ] 有真实用户（≥3 人）
- [ ] README 三分钟内能跑通，有动图与架构图
- [ ] 仓库里不出现任何真实机构的数据与名称
