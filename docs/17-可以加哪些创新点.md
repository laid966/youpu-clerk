# 17 · 还能加哪些创新点（在现有结构下）

> 判断标准只有一条：
>
> **能不能产出一个"别人拿不到的数字"？** 能，才算创新点；不能，就只是换个说法。

---

## 零、先说清楚：有三条我们已经铺开但**没做完**

别急着加新的，这三条是半成品，做完的性价比比新开一条高。

| | 现状 | 差什么 |
|---|---|---|
| **注入器插件化** | `audit/inject.py` 里 `_INJECTORS` 已是注册表的形状，但没对外开放；9 类注入还是医学专用的 | 让插件能声明自己的缺陷类型，第二个场景才有完整基准 |
| **产物适配器** | `Artifact` 的形状够用（判定+说法+依据+数值），但字段名和"参考区间"语义是医学味的 | 一个薄适配层，把非医学产物映射进来 |
| **人工复核回流** | `human_review` 节点只设了个标记 | 回流通道：人工判定 → 补进基准（真阳）／补进高难度负例（误报） |

**其中"人工复核回流"是唯一会自己长大的机制**——它让准确性产生复利。
没有它，准确性只能靠人手写句子提升。

---

## 一、推荐加的三条（按"真新 × 可做"排序）

### ★ ① 判定稳健性审计（Verdict Robustness / 判定脆弱性）

**是什么**：把原始数值在**测量误差范围内**扰动（比如 ±1×实验室允许误差、±1%），
重新用 oracle 重算，看判定会不会翻转。

**为什么只有我们能做**：这需要**独立 oracle**。
引用类/groundedness 工具原理上做不了——它们没有"重算"能力。

**它产出的新东西**——**一类全新的发现**，而且**不是注入的**：

```
[verdict_fragility] 肌酐 的判定在测量误差范围内会翻转
  当前值 73 umol/L → mild（轻度偏离）
  若实测偏差 -1%（72.3）→ normal
  说明：这条结论离阈值太近，不宜作为定论
```

**为什么这个最有价值**：到目前为止，我们所有的召回率都建立在
"**缺陷是我注入的**"之上——所以那个数字永远可以被人说成"你只测了你造的题"。
**而脆弱性是"发现"出来的性质，不是造出来的。** 这是我们第一次能说：

> **"这个结论在数据测量误差范围内不稳定，所以它不该被当成定论。"**

这句话是**产品价值**，不是评测指标。

**产出什么数字**：**判定脆弱率**（fragile verdict rate）= 脆弱项 / 全部项。
以及**每个判定离阈值有多近**（做成一栏"余量"，最直观）。

**怎么做**：`judge_metric` 已经有了；加一个扫描器，在 ±ε 上取几个点重算。
**零模型调用、零成本、完全确定性。**

**工作量**：小（半天内）。**风险**：低。

**⚠️ 一个必须你来定的产品问题**：脆弱项**算不算缺陷**？
- 算 → 召回率会上升（但语义从"AI 抄错了"变成"结论不稳"）
- 不算 → 它是一种**风险提示**，单独一类，不影响召回/误报

**这是产品判断，不是技术判断**（归到你的 `docs/02-metrics.md`）。

---

### ② 对抗式逃逸搜索（Adversarial Evasion）

**是什么**：不再用**固定**的注入句，而是**搜索**能骗过审计器的产物：
在"仍然违规"的前提下，反复改写包装方式，留下那些**能逃过检查**的版本。

**为什么比现在强**：现在的召回率是"在**我知道的 32 句话**上考出来的"。
对手一换说法就可能掉。逃逸搜索把问题升级成：

> **不是"你能不能抓住我出的题"，而是"你能不能挡住一个专门研究你的人"。**

**产出什么数字**：**逃逸率**（evasion rate）= 逃过的变体 / 尝试的变体。
以及**每个检查器的可逃逸性**排名（哪个检查器最容易被绕）。

**怎么做**：复用注入器 + 一个变异/搜索循环（同义改写、语序调整、包装成科普）。
可以用模板，也可以让模型生成变体（那就花钱，但更真实）。

**工作量**：中（一两天）。**风险**：中——搜索空间大，要设上限才不失控。

**⚠️ 诚实提醒**：这条最"科研"，但也最容易做成"看起来很凶、其实没测到东西"。
**必须有上限、有基线（固定注入的召回）、有对比**，否则不如不做。

---

### ③ 审计的确定性（同一个产物，两次审计结果一样吗）

**是什么**：同一份产物，跑 N 次，看报出来的发现是否完全一致。

**为什么重要**：生产环境里，**审计结论要能作为证据**。
如果同一个输入两次给出不同的结论，这个系统**没法用来做放行决策**——
出了问题你无法解释"当时为什么没报"。

**为什么几乎没人测**：因为大多数人的审计器**就是不确定的**，测了不好看。
我们不一样：确定性层是确定的，只有语义层受模型影响——
**所以我们可以精确地把"哪一部分不确定"量出来。**

**产出什么数字**：
- **发现稳定性**（Jaccard：两次发现的交集 / 并集）
- **语义层翻转率**（同一文本，判定 true/false 变化的比例）
- **首次即一致率**

**怎么做**：`--no-cache` 重跑 N 次，比对发现集合。**花钱**（N× 调用），
所以默认跑小样本（比如 20 条 × 3 次）。

**工作量**：小。**风险**：低。

**⚠️ 预期结果**：很可能**不是 100%**。
那也没关系——**把真实数字报出来，比假装确定强得多**，
而且它直接指向一个工程解法：**缓存 + 固定 seed + 低温度**（我们已经有缓存了）。

## 二、另外两条（值得做，但不算"新"，算"更好用"）

### ④ 最小修复建议（Minimal Fix / 增量调试）

报错是一回事，**告诉人怎么改**是另一回事。给定一条发现，
找出**最小的改动**让它合规（改哪几个字、把数值改成什么、把建议换成哪句）。

出处是经典技术：**delta debugging / 反例最小化**。
不是新东西，但**从"报错"到"给最小修复"是产品体验的质变**，
而且能直接接上补丁闭环（`agent/patch.py` 现在只提护栏规则）。

产出数字：**修复建议的可执行率**（建议采纳后，发现真的消失的比例）。

### ⑤ 预算最优分配（Cost-aware Semantic Scheduling）

现在是"固定范围"（`abnormal_only` / `all`）。升级成：

> **在成本预算下，决定"哪几条送模型"来最大化召回。**

依据是**期望收益**：这一条有多大可能存在语义越界 × 抓到的价值 ÷ 单次成本。
用已有的数据估：**分档缺陷密度**（危急档更容易出事）、**余量**（离阈值近的更可疑）、
**历史误报率**。

产出数字：**召回-成本帕累托曲线**（而不是一个点）。
现在的对比是"23 次调用 / 92%"vs"237 次调用 / 100%"，
最优分配应当给出**中间那些点**上更好的解。

**工作量**：中。**风险**：中（容易过拟合到基准）。

## 三、明确标为"包装"的（我建议不做）

| 想法 | 为什么不算创新 |
|---|---|
| 换成更强的模型 | 谁都能换，和我们的架构无关 |
| 加向量检索 | 成熟技术；已经列在 A6，属于"补作业"不是创新 |
| 加更多场景 | 是**规模**，不是创新（但它是"可扩展"的证据，仍然值得做） |
| 界面做漂亮 | 演示价值有，创新价值零 |
| 上多智能体协作 | 现在没有证据表明它能提升召回，先别加 |

## 四、我的建议顺序

```
第一步  判定稳健性审计（①）        ← 唯一"只有我们能做"、且零成本
第二步  审计的确定性（③）          ← 生产必需，数字诚实
第三步  人工复核回流（零节里的）    ← 唯一会自己长大的机制
第四步  对抗式逃逸搜索（②）        ← 最有科研味，但要设上限
第五步  最小修复建议（④）          ← 体验质变，接补丁闭环
```

**为什么 ① 排第一**：它把我们最核心的资产（独立 oracle）用出了**新 用途**——
从"检查 AI 抄错了没有"扩展到"**检查这个结论稳不稳**"。
而且它产出的第一句话就是**面向用户的价值**，不是自娱自乐的指标：

> **"这个结果离临界值太近，不宜作为定论。"**

这句话任何 groundedness 工具都产不出来。**这就是"别人拿不到的数字"。**

---

## 五、加创新点时要守的两条纪律

1. **必须有基线**。任何新指标都要和"不做它"的情况对比，否则数字没有意义。
   （我们吃过亏：`safety_paraphrase` 加进去，召回从 100% 掉到 87.9%——
   那不是退步，那才是真数字。）
2. **必须写进测试**。新能力如果没有测试守着，它会**静默退化**。
   项目里已经有一类专门的守卫测试（`tests/test_invariants.py`）。
