# 16 · 优势与创新点（说给面试官听的版本）

> 这份文档回答两个问题：**我们的优势在哪？创新点在哪？**
>
> ⚠️ 规矩：**不许把成熟技术说成自己的发明。** 被追问一层就露底，比不说更糟。

---

## 一、一句话结论

> **我们的优势不在"发明了什么"，而在"把三件通常分开做的事绑成了一个闭环"——
> 因此我们的数字是**可证伪的**，而大多数同类项目的数字不可证伪。**

"三件事"是：

| | 通常谁做 | 我们怎么做 |
|---|---|---|
| **造标准答案** | 人工标注，或用另一个模型评 | **注入式缺陷基准**：标准答案是绝对的 |
| **判对错** | 让模型自查，或查"有没有依据" | **独立确定性 oracle 重算** |
| **证明这套评测本身可信** | 一般不问 | **变异测试 + 置信区间** |

**第三件是分水岭。** 大多数项目只做前两件，所以它们的召回率"不可证伪"——
你没法知道那个数字是真实水平还是运气／自我循环。

---

## 二、四条真正的差异（按值钱程度排序）

### ① 问题定义不同：从"有没有依据"到"判定对不对" ★最核心

现在主流工具（groundedness / attribution / RAG 评测那一类）回答的问题是：

> **"这句话有没有证据支持它？"**

我们回答的是：

> **"这个判定本身对不对？"**

**这不是技术差异，是问题定义的差异。** 为什么它重要：

- 一个**判定错的**产物，往往**全文自洽、引用全都真实存在**。
  它唯一的问题就是"算错了"。
  → **引用类工具对它 100% 无效**（不是效果差，是原理上就抓不到）。
- 反过来，"判定正确"的产物也可能引用错。两者是**正交**的两件事。

**所以稀缺性的来源不是"某个功能没人做"，而是"这个问题很少有人这么定义"。**

而它成立有一个前提，这个前提正是我们的机会所在：

> **判定类输出有"对错"，而生成类输出只有"好坏"。**
> 有对错 → 可以用独立 oracle 重算 → 差分审计可行。
> 生成类（写文章、聊天）没有对错 → oracle 不存在 → 只能退回 groundedness。

### ② 可检测性契约：造数据的和判对错的必须是同一套语言

我们有一条**三方闭合的契约**：

```
缺陷类型（注入器能造出来）
    ↕  DEFECT_KINDS
检查器（能检出来）
    ↕  DETECTOR_TO_KINDS
预期检查器（评测按 (检查器, 目标) 配对）
```

**三处必须对得上，而且有测试守着。** 这条约束的作用是：

> 防止"我造了一个错，但没有任何检查器该抓它"——
> 那种缺陷进了基准，召回率的分母就是假的（永远抓不到，等于人为压低召回）。
> 也防止反过来：检查器报了一堆基准里没有的东西，被算成误报。

**大多数项目的 benchmark 和 detector 是分开做的**，所以两边的口径慢慢就漂了。
我们把它们绑在一起，**并且用契约测试钉住**。

### ③ 对"评测本身"的怀疑 ★最容易被忽略、也最难做

这一条不是功能，是**工程习惯**，但它产出了全项目最有说服力的证据：

- 建立了**变异测试**框架：故意改坏流水线，看测试抓不抓得住
- 过程中抓到**两个伪造 100% 的机制**：
  - 沙箱基线本身就是红的 → 每个变异体都显示"被杀"
  - 一条元测试对**任何**变异都失败 → 同样伪造"全部被杀"
- 因此引入**基线自检**和**元测试排除**，并区分"必须杀死"与"允许存活的旋钮"
- 明白了**两类 100% 必须分开**：闭环验证的 100%（缺陷是按检查器能力造的）
  和能力证明的 100%（拿没见过的东西测）

**面试时这一条最能加分**，因为它证明的不是"我会做功能"，而是
**"我会怀疑自己的数字"**。

### ④ 可声称范围的自觉

- 指标带**置信区间**（Clopper–Pearson），不是裸百分比：
  `24/24 全对` 的正确读法是"真实召回 ≥ 88.3%"，**连 90% 都声称不了**
- 样本量是**算出来的**，不是攒的：要声称 ≥95%，零失败时需要 59 条
- 明确标注**闭环验证 ≠ 能力证明**
- 报告里直接打印"**这份成绩能证明什么**"，包括"**还不能**声称什么"

**这条在 LLM 评测里很少见**——大家习惯报一个百分比就完事。

## 三、诚实清单：这些**不是**我们的创新

| 我们用的 | 它的真实出处 |
|---|---|
| 内核 + 插件分离 | **Microkernel / Plugin Architecture**，软件架构教科书里的成熟模式 |
| 内核定接口、外部插实现 | **Ports & Adapters**（Alistair Cockburn） |
| 规则是数据，引擎通用 | **OPA（开放政策代理）**：开源的通用策略引擎 |
| 加场景 = 加配置 | **lm-evaluation-harness**：加一个 task 就是加一份 YAML |
| 可插拔的校验器目录 | **NeMo Guardrails + Guardrails AI** |
| 提示词注册与版本管理 | **Prompt registry / PromptOps** |
| 独立 oracle 交叉验证 | **Differential Testing / N-Version Programming**（航电容错经典） |
| 故意注入缺陷量召回 | **Fault Injection**（安全与可靠性工程的常规手段） |
| 改坏代码看测试抓不抓 | **Mutation Testing**（1970 年代就有） |
| 小样本的置信区间 | **Clopper–Pearson 区间**，标准统计方法 |

**一行都不是我们发明的。** 而且 2026 年这个方向正在被填——
已经有 [N-Version Programming with Coding Agents](https://arxiv.org/html/2606.20158v1)、
[SmartOracle（differential oracles）](https://web3.arxiv.org/pdf/2601.15074) 这类工作。

**所以正确的说法是**：

> **"这个组合我没有查到现成的同类产品，所以我按自己的口径把闭环走完了，
> 并且用可复现的数字证明它成立。"**

"没查到" ≠ "没有"。**把前者说成后者，是最容易被拆的吹法。**

## 四、为什么"不是首创"反而是好事

| 如果我说"我发明了新架构" | 如果我说"我用成熟架构解决了这个问题" |
|---|---|
| 面试官会找一个学名来反驳你 | 面试官会问"你怎么用的"——**这正是你准备好的** |
| 显得没见过世面 | 显得有底子 |
| 经不起一次追问 | 可以连着答三层 |

**加分的地方不在"首创"，在"闭环 + 证据 + 承认边界"。** 这三样都比"首创"难。

## 五、对比表（可以直接拿去讲）

| 环节 | 常规做法 | 我们 | 差别是什么 |
|---|---|---|---|
| 审计对象 | 说法有没有依据 | **判定本身对不对** | 问题定义不同 |
| 兜底手段 | 让模型自查 | **独立确定性 oracle** | 不会自己批改自己的卷子 |
| 标准答案 | 人工标注 | **注入式缺陷**（答案绝对） | 可复现、可扩样本 |
| 造数据与评测 | 分开做 | **三方契约 + 测试守着** | 口径不会漂 |
| 报告指标 | 一个百分比 | **点估计 + 置信区间 + 能声称什么** | 可证伪 |
| 评测本身可信吗 | 不问 | **变异得分 + 基线自检** | 证明测试有效 |
| 加第二个场景 | 改代码 | **加一个插件目录**（有测试守着） | 边际成本低 |
| 跑通 CI | 要 key、花钱 | **离线、零成本** | 别人 fork 就能跑 |

## 六、一句话定位 + 三段话术

**定位**：

> 一个**插件化的、判定类 LLM 输出的差分审计框架**——
> 用独立 oracle 重算来找模型的错，并**证明这套评测本身可信**。

**① 讲架构**（不要讲成"我发明的"）
> 我把它做成了 microkernel 架构：内核只负责机制——规则求值、缺陷检测、审计图编排；
> 场景相关的规则、字段清单、词表、提示词、知识库全是插件内容。
> 换一个行业只加一个目录，内核一行不改，**这个有测试守着**。

**② 讲方法**（这是你真正的差异点）
> 审计用的是**差分测试**：不是让模型自查，而是用独立的确定性 oracle 按原始数据重算、
> 比对判定。引用类工具抓不到"判定错了但全文自洽、引用全真"这一类——
> 那是原理上抓不到，不是效果差。

**③ 讲证据**（最能加分的一段）
> 我把三件事都做成了数字：**标准答案怎么造**（注入式基准）、
> **结论能声称到什么程度**（置信区间，不是裸百分比）、
> **测试本身有没有用**（变异测试，过程中抓到两个伪造 100% 的机制）。

## 七、诚实的边界：什么情况下我们的优势不成立

这一节比前面都重要——**知道自己在哪不行，才守得住哪行。**

| 情况 | 我们还有优势吗 |
|---|---|
| 场景**没有可写的规则集** | ❌ **没有。** 没有规则就没有 oracle，差分审计无从谈起，只能退化成 groundedness——而那个领域已有成熟工具，我们打不过 |
| 输出是**生成类**（写文章、聊天） | ❌ 没有。生成类只有好坏没有对错，oracle 不存在 |
| 判定标准**本身有争议**（比如"该不该放款"） | ⚠️ 部分。oracle 只能重算"按既定规则对不对"，算不了"规则本身对不对" |
| 判定标准**明确且有规则集** | ✅ **有。** 这正是我们的主场：体检分级、信贷审批、理赔核定、资格判定 |
| 需要有**可审计、可复现**的质检数字 | ✅ 有。这正是我们比"让模型自查"强的地方 |

**所以我们的适用边界一句话**：

> **凡是"有明确规则、输出带判定"的 AI 系统，我们都插得进去；
> 反过来，规则不明确或输出没有对错的场景，我们插不进去。**

这条边界要在**产品文档（`docs/01-prd.md`）里明确写出来**——
说清"不做什么"比说清"做什么"更显专业。
