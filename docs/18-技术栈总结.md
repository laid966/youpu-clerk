# 18 · 技术栈总结：我们到底用了 LangChain / LangGraph 的什么

> 这份文档是为了回答面试里最容易被问倒的一句话：
> **"你说你用了 LangGraph，那你具体用了它什么？"**
>
> 结论：**用得非常少，而且是刻意的。**

---

## 一句话结论

> 全项目只用了 **LangGraph 的图编排** + **langchain-deepseek 的模型接入**，
> 一共 **4 处导入**。
> **没有用** LangChain 的 Chain / Agent / Tool / Memory / Retriever 抽象，
> 也**没有用**它的 Output Parser 和 PromptTemplate。

**这不是"没学会"，是"用了之后发现它挡路"。** 下面逐条说清。

---

## 一、逐处清单（全项目共 4 处）

| 位置 | 导入的什么 | 用来做什么 | 为什么用它（而不是自己写） |
|---|---|---|---|
| `agent/graph.py:19` | `from langgraph.graph import END, StateGraph` | 装配审计图：`add_node` / `add_edge` / `add_conditional_edges` / `compile` | 需要**有条件分支 + 状态在节点间流转**。手写会退化成一堆 `if state["..."].`，而且没有可视化 |
| `agent/cli.py:128` | `from langgraph.checkpoint.sqlite import SqliteSaver` | `--persist` 时把图状态落盘（可续跑、可回放） | "录制回放"是部署要求；自己实现序列化 + 恢复不值得 |
| `agent/judge.py:49` | `from langchain_deepseek import ChatDeepSeek` | **唯一的模型入口**（真实调用） | 官方接入，省掉自己写 HTTP / 重试 / 消息格式 |
| `main.py:24` | 同上 | 冒烟脚本：验证密钥与连通性 | 同 |

**除此之外，整个仓库没有任何 LangChain / LangGraph 的调用。**

## 三、明确**没有**用的东西（面试高频追问）

| LangChain 提供的能力 | 我们没用，用什么代替 | 为什么 |
|---|---|---|
| **LCEL / Chain** | 自己写的节点函数（`agent/nodes.py`）+ 图（`agent/graph.py`） | 节点里要做**确定性控制**：成本上限、证据校验、升级人工。Chain 的隐式行为会把这些挡住 |
| **Agent / Tool** | 没有工具调用 | 审计步骤是**固定的**（规划→确定性检查→语义检查→反思→裁决），不需要模型自主决定下一步 |
| **Memory** | 无 | 每次审计相互独立。跨会话记忆在这里是风险不是功能 |
| **Retriever 抽象** | 自写 BM25（`rag/bm25.py` + `rag/tokenize.py`） | 要能精确控制分词、停用词、字段加权，**并且要能量出可比的基线**。封装的检索器说不清自己怎么算的 |
| **Output Parser** | 手写 JSON 解析，**解析失败即记为"错误"** | LangChain 的 parser 会把解析失败兜底成空/默认结果 —— 那等于**把失败伪装成"没违规"**，是本项目最危险的失败模式 |
| **PromptTemplate** | 裸字符串 + `{text}` 占位（`agent/prompts.py`） | 提示词要能被**版本注册表**管理（`_REGISTRY` → v1/v2 对比），不需要模板引擎。而且插件要能自带自己的提示词 |
| **Callbacks / Tracing** | SQLite 结果缓存（`data/judge-cache.db`） | 我们要的是**可复现 + 不重复花钱**，不是调用链追踪 |

## 四、为什么"用得少"反而是优势

面试时这三句话可以直接用：

**① 确定性优先**
> 审计器里凡是能用程序判的，我都不交给模型。所以流程编排只需要"图 + 状态 + 条件分支"，
> 不需要 Chain 那种把逻辑藏进抽象层的写法。**抽象层省下的代码，会以"说不清为什么这么判"的形式还回来。**

**② 失败必须显形**
> 我没用 LangChain 的 output parser，因为它在解析失败时会兜底。
> 在审计场景里，模型返回值读不懂**必须报错**，不能当成"没发现问题"——
> 那会把失败伪装成正确。所以我把解析失败单独计一个数，目标是永远为 0。

**③ 要能自证**
> 检索是我自己写的 BM25，不是因为它简单，是因为我要能回答
> "Recall@1 从 74.2% 提到 93.5% 是哪三处改动带来的"。
> 封装得越深，越说不清数字是怎么来的。

## 六、这套技术栈的边界（诚实说）

| 现在没有 | 什么时候需要 |
|---|---|
| 调用链追踪（tracing） | 要上生产、排查"这次为什么慢/贵"时才需要 |
| 多模型 provider 切换 | 要给不同客户用不同模型时 |
| 流式输出到前端（逐字） | 现在只有**逐节点**流式（SSE 推进度），前端体验够用 |
| 提示词的运行时热更新 | 现在改提示词要重启服务；上线前应该做成配置 |

**这些都是"上线前要补的作业"，不是"现在缺的能力"。**
把它们写在这里，是为了面试时能主动说出边界——**主动交底比被问出来强。**
