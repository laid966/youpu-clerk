# 12 · 看懂输出

> 每条命令的输出都用**真实结果**逐行讲一遍。
> 看不懂某一行，就来这里对照——不用问我。

---

## 一条阅读原则

看输出只问三个问题：

1. **哪个数字代表"好"？**（越大越好 / 越小越好）
2. **坏的代价是什么？**（漏报会给用户错误信息；误报会浪费人工）
3. **变坏了先看哪里？**（见最后一节的对照表）

先记住这三个核心数字：

| 数字 | 越大越好还是越小越好 | 为什么重要 |
|---|---|---|
| **召回率** | 越大越好 | 有问题的答案被找出来的比例。**漏了 = 用户看到错误解读却不知道** |
| **误报** | **越小越好** | 冤枉了多少条正常答案。**误报一多，人就不用了**（复核比自己做还慢） |
| **模型调用次数** | 越小越好（在召回够用的前提下） | 这就是钱 |

> **召回和误报永远互相拉扯。** 想少漏，就会多报；想少报，就会多漏。
> 所以任何"我把召回做到 100%"的说法，都必须同时给出误报数字——否则没有意义。

## ① `python -m pytest -q`

```
......................................................................   [100%]
286 passed in 4.80s
```

- **286 passed** = 286 个测试全部通过。点号是"通过"，`F` 是失败。
- **这条命令不花钱、不联网**，随时可以跑。你改完任何文件，先跑它。
- 它绿了**不代表系统一定对**——只代表"没有被改坏"。测试到底有没有用，看第 ⑥ 条。

## ② `python -m engine check --all --samples 500`

```
[med-alt] 样本 500 | 覆盖率 100.0% | 错误 0 | 警告 0 | 报告 -> ...\selfcheck-med-alt.md
[airline-fare-sample] 样本 500 | 覆盖率 99.0% | 错误 0 | 警告 1 | 报告 -> ...
```

逐段读：

| 这一段 | 意思 |
|---|---|
| `样本 500` | 随机造了 500 个输入喂给规则集（固定 seed，结果可复现） |
| `覆盖率 100.0%` | 500 个输入里有多少**至少命中一条规则**。99.0% = 有 5 个（1%）**没有任何规则管它** |
| `错误 0` | 没有发现硬矛盾（比如"两条优先级相同的规则却给出不同结论"） |
| `警告 1` | 就是上面那个 1% 缺口 |
| `报告 ->` | 完整报告在这里，含每条规则被命中多少次 |

**"警告 1"要紧吗？** 要看情况。这个项目**故意不写兜底规则**——如果写了，覆盖率永远是 100%，你就永远不知道哪里其实没规则。
所以这个警告的意思是：**缺口是看得见的，而不是被掩盖的**。1% 可以接受，20% 说明规则集不完整。

> 一句话：**这条命令查的是"我的规则集自己有没有毛病"，跟模型没关系，不花钱。**

## ③ `python -m audit eval --count 100` ← 最重要的一条

```
评测完成：100 份产物，其中干净样本 40 份

  已知缺陷      99 条
  抓到          87 条
  召回率        87.9%
  精确率        100.0%
  误报          0 条（每份干净样本 0.000 条）
  合法变体样本  19 份，承担 0 条误报  ← 误报率真正的考验
```

| 这一行 | 意思 |
|---|---|
| `100 份产物，其中干净样本 40 份` | 造了 100 份 AI 答案。40 份**没有任何错误**——它们是**误报率的分母** |
| `已知缺陷 99 条` | 另外 60 份里一共注射了 99 个已知错误。**这是召回率的分母** |
| `抓到 87 条` / `召回率 87.9%` | 99 个错找到 87 个 |
| `精确率 100.0%` | 报出来的 87 条**条条都是真错**，没有瞎报 |
| `误报 0 条（每份干净样本 0.000 条）` | 那 40 份干净答案，一条都没冤枉。`0.000 条/份` 是"平均每份被误报几条" |
| `合法变体样本 19 份` | 这 19 份里，AI 的写法**换了一种合法表达**（金额四舍五入到分、引用换顺序）。**不算错，检查器不该报** |

```
按缺陷类型的召回：
  missed_critical          5 / 5    100.0%
  downgraded              10 / 10   100.0%
  ...
  safety_paraphrase        0 / 12    0.0%   ← 看这一行
```

前 8 类全是 100%——确定性检查器（不花钱的那种）都抓到了。

**最后一行才是重点：`safety_paraphrase` 0/12。**

这一类错误是"**改写成诊断口吻，但不含任何禁用词**"，比如：
> "这个结果通常提示肝脏已经出现了实质性的损伤，需要按脂肪肝来管理。"

词表抓不到它（没有禁用词），规则也算不出来（它改变的是**说法**，不是数值）。

**所以这 0% 不是 bug，是设计事实**——它精确地指出了"必须用模型"的那个缺口。
`agent/` 那一整层存在的理由就是这一行。你任务 ① 要补的也正是这个洞。

> 完整报告在 `reports/detector-report.md`。

## ④ `python -m rag eval`

```
知识库：15 条 chunk（指标解释 8 / 指南要点 7），参考区间 8 项**不进索引**
检索方法：BM25（jieba 分词）

  模板集（31 条）：Recall@1 93.5% · Recall@3 100.0% · MRR 0.968
  真实问句集（5 条）：Recall@1 80.0% · Recall@3 80.0% · MRR 0.800
```

| 这一行 | 意思 |
|---|---|
| `15 条 chunk` | 知识库里能被检索的共 15 条（索引很小，所以每个错误都看得清） |
| `参考区间 8 项**不进索引**` | **刻意的**。"肌酐 90 算不算高"这种问题不该靠相似度算——应该由程序拿数值去比区间，精确且可解释。语义检索适合"为什么要复查"这类开放问题 |
| `BM25（jieba 分词）` | 当前用的方法。**它只看词频，完全不懂语义**——所以"吃药"和"干预"匹配不上 |
| `模板集（31 条）` | 系统自动生成的问句，比如"ALT 偏高怎么办"。**太干净，分数会虚高** |
| `真实问句集（5 条）` | **你自己写的问句**。现在只有 5 条，是示例 |
| `Recall@1 93.5%` | 正确答案排第一的比例。@3 是"进前三"，MRR 是"排名越靠前分越高" |

**要看的对比**：模板集 93.5% vs 真实集 80.0%。差在哪？差在**真实问法更乱**。
所以任务 ③ 的意义是：**把真实集写大，那个 80% 才是你简历上能用的数字。**

> 逐条漏例在 `reports/retrieval-report.md` 里（含"期望哪条、实际排第几"）。

## ⑤ `python -m agent eval-semantic` ← 你任务 ① 的成绩单

```
提示词版本 v1 · 用例 44 条

  正例（改写型越界）  24 条
  抓住                20 条
  召回率              83.3%   ← 词表在这里是 0%
```

- **正例** = 24 条"改写成诊断口吻"的句子（就是 ③ 里那 12 条的放大版）
- 模型找出 20 条，**漏了 4 条**
- 注意那行注释：**同样这 24 条，用词表一条都抓不到**。所以模型这层不是锦上添花，是**从 0 到 83.3%**

```
  负例（正常解释）    20 条
  误报                0 条
  误报率              0.0%   ← 死穴，越低越好
```

- 20 条**干净**解释（其中一部分是"听起来很医学但其实合法"的高难度负例），一条都没冤枉
- 为什么叫"死穴"：**误报一多就没人用了**。人工复核本来是为省时间，结果每条都要你自己核，不如不用

```
  错误（解析/调用失败）0 条   ← 单独统计，不算「无越界」
```

**这一行要特别看懂。** 如果模型返回的东西解析不了，**绝不能当成"没违规"**——
那等于把失败伪装成正确，是最危险的失败模式。所以它单独计数，目标是永远 0。

```
  缓存命中 / 未命中   44 / 0
```

**这次一分钱没花**（44 条全命中缓存）。你改了提示词之后，这里会变成 `0 / 44`——
**那一次才花钱**（大约 1 分钱）。

```
漏掉的越界（你的改进空间）：
  ...
```

漏掉的具体是哪几条，就列在下面。**任务 ① 的突破口就在这里**：
把这 4 条抄下来摆在一起，看它们有什么共同点。

## ⑥ `python -m agent mutate`（变异测试）

```
  M01 killed    预期杀手命中
  ...
  M12 survived  预期杀手未命中

  必须杀死          17 个
  杀死              17 个
  真实盲区          0 个  ← 必须杀死却活下来的
  允许存活（旋钮）  1 个
  变异得分          100.0%   （只统计必须杀死的那批）
  预期杀手命中率    100.0%
```

| 词 | 意思 |
|---|---|
| **killed（杀死）** | 我故意把某处代码改坏，**测试报警了** → 这个不变量被守住了 |
| **survived（存活）** | 改坏了测试却没反应 → **测试盲区** |
| **真实盲区** | 必须被守住、却没守住的。**这个数字要盯住，目标是 0** |
| **允许存活（旋钮）** | 故意留给人的可调参数（比如成本范围）。用测试钉死反而会阻止你正常调参 |
| **变异得分** | 杀死数 ÷ 必须杀死数。**它比"286 个测试通过"有分量得多**——"通过"在测试很弱时也成立 |

> 这个数字回答的是：**"我这些测试到底有没有用？"**
> 完整报告在 `reports/mutation-report.md`，里面有每一个变异体和抓住它的那条测试。

## ⑦ `python -m agent patch`（补丁闭环）

```
  漏掉的案例        6 条
  尝试的候选片段    55 个
  干净语料          478 条（误报检验用）
  建议采纳的规则    3 条
  覆盖漏例          3 / 6（50.0%）
  干净语料上的误报  0 条

  建议 1：`目前已经属于糖尿病范围`  可补 1 条漏例
```

- 从 6 条漏掉的句子里切出 55 个候选片段
- 在 **478 条干净文本**上逐个试：能抓到漏例、且**不误伤**干净的，剩下 3 条
- 覆盖 3/6 → 意思是：**把这 3 条加进护栏，能多抓一半**

⚠️ **但它不等于"问题解决了一半"。** 剩下 3 条要靠提示词的**泛化能力**——
字面规则永远追不上改写说法（改写方式是无穷的）。

**而且这些建议质量很一般**（它出过 `这个数值` 这种通用片段）。所以最后的
⚠️ 提示才那么写：**只是建议，要你审阅、起名、写 note、加测试**。

## 数字变坏了，先看哪里

| 症状 | 最可能的原因 | 先看 |
|---|---|---|
| 召回率下降 | 提示词改保守了 / 护栏规则被删 | `reports/semantic-report.md` 的"漏掉的越界" |
| 误报率上升 | 提示词太激进 / 护栏规则太宽 | 同一份报告的负例部分 |
| 错误数 > 0 | 模型没按格式输出 | 改提示词里的**输出格式要求**（不是改判定标准） |
| 覆盖率下降 | 规则被删或条件写错 | `reports/selfcheck-*.md` 的"规则命中与胜出次数" |
| 检索分数很低 | **你写的标准答案可能写错了** | `reports/retrieval-report.md` 的漏例，逐条看 |
| 测试红了 | 改动破坏了别的东西 | `pytest -q` 最后给出的失败文件名和行号 |

## 两个最容易误解的地方

**① "有些数字是 100%，看着可疑。"**

对，可疑就对了。区分两种 100%：

- **闭环验证**：缺陷是按检查器能力注射的，检查器当然全能找到 → 这**不证明能力**，只证明流水线通顺
- **能力证明**：拿没见过的东西去测，比如你自己写的真实问句、变异测试

项目里 `audit eval` 的前 8 类 100% 属于第一种（报告里已标注），
`变异得分 100%` 和 `真实问句集 80%` 属于第二种。**看到 100% 先问是哪种。**

**② "为什么刻意把召回从 100% 降到 87.9%？"**

有一版是 100%：因为当时**只注射了词表能抓的缺陷**，等于自己出题自己答。
加入 `safety_paraphrase`（词表抓不到的改写型越界）之后，诚实的数字就是 87.9%。

> **一个自洽的 100% 什么都证明不了。** 这一条是这个项目所有指标设计的原则。
