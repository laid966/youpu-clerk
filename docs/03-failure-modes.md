# 03 · 失败模式分析

> 这份文档是本项目**最能体现判断力**的部分。招聘方明确说过两件事：
> 1. 主动讲失败案例比只讲成功更有说服力；
> 2. 面试会追问"最意外的失败是什么""为稳定性删掉过什么链路"。
>
> 所以这里不写成功，只写"哪里错了 → 为什么错 → 怎么改 → 改完用数据复测"。

---

## 使用规则

每个失败模式一条，编号 `FM-001` 起，四段式固定结构：

| 字段 | 要求 |
|---|---|
| 现象 | 一句话描述用户看到的问题（不要写"模型不好"这种空话） |
| 复现 | 给出可复现的最小输入，别人照着能重现 |
| 归因 | 到底是哪一层的问题：数据 / 规则 / 模型理解 / 提示词 / 代码 / 我的设计 |
| 改法 | 具体改了什么（改代码、改规则、改提示词、改流程） |
| 复测 | 改完后的数据：第几条用例从"错"变"对"，整体指标怎么变 |
| 状态 | 已修复 / 已知不修（写原因）/ 待观察 |

**硬性要求**：至少 8 条；其中至少 1 条必须是"**主动砍掉的功能**"（见文末模板）。

## FM-001 · 待你用网页版聊天工具做实验后填写

**实验步骤**（约 3 分钟）

1. 打开任意网页版聊天工具（不要用本项目的代码）。
2. 构造一条稍微绕的虚构规则，例如：

   > 退票费率按离站时间分档：提前 7 天以上收票面 5%，7 天内至 48 小时前收 15%，
   > 48 小时内收 30%。若票面折扣低于 5 折，上述费率各加 10 个百分点。
   > 联程票已使用其中一段的，按未使用航段比例折算票面后再计费。

   再给一张具体订单，例如：

   > 订单号 A-1001，票面价 15000 元，经济舱，折扣 4 折，联程两段（第一段已使用），
   > 距离第二段起飞还有 5 天，现要求退第二段。

3. **同一个问题连续问三次**（不要改措辞）。

## FM-002 · 同优先级规则被误报成"优先级冲突"（引擎 bug）

**现象**：学位审核域的转人工原因里出现 **1172 次**
「规则优先级冲突：U-002 与 U-003 同为优先级 20 但结论不同，需人工裁决」。
但 U-002 与 U-003 的结论**完全一样**（都是 `not_eligible`，都不涉及金额）。

**复现**：

```bat
.\.venv\Scripts\python.exe -m engine check --domain domain/university-credit-sample/domain.yaml
```

或直接判定一组 `total_credits < 60` 且 `core_credits < 36` 的事实。

**归因**：代码层，不是规则层。冲突判定写成了 `item != winner`，而 `MatchedRule`
是包含规则 id 的数据类——于是**任何同优先级的第二条规则**都会被判为"不同"。
真正暴露它的是两个模块互相矛盾：`engine/selfcheck.py` 用的是"只比结论"的正确逻辑，
报告里写着"未发现错误级问题"；而 `engine/adjudicate.py` 却在每次判定时报冲突。
**同一批数据、两个模块、相反结论——矛盾本身就是定位 bug 的线索。**

**改法**：
1. 判定冲突时只比较结论元组 `(verdict, fee_amount)`；
2. 补回归测试 `test_same_priority_same_conclusion_is_not_a_conflict`，
   同时保留"同优先级且结论不同时必须转人工"的用例，防止为了修误报而把真问题一起放过。

**复测**（改前 → 改后）：

| 指标 | 改前 | 改后 |
|---|---|---|
| 报告里"优先级冲突"行数 | 1172 | **0** |
| 学位域 `not_eligible` 条数 / 3000 样本 | 19 | **235** |
| 学位域 `needs_review` 条数 / 1000 条用例 | 978 | **762** |
| 测试总数 | 103 | 104 |

**状态**：已修复

## FM-003 · 评测数据集的分布严重失真（已知，暂不修）

**现象**：生成 1000 条用例后，**89.5%**（airline 域）与 **76%**（university 域）
的结论是"转人工"。照这个数字看，这套系统几乎没有自动化能力。

**复现**：

```bat
.\.venv\Scripts\python.exe -m engine gen --all --count 1000
```

然后统计 `dataset-*.jsonl` 里 `expected.final_verdict` 的分布。

**归因**：**设计层（生成器的取样分布），不是引擎。**
布尔字段按 50/50 均匀取样、航段数独立取样，于是"误机""联程已使用一半"
"已用航段数大于总段数"这些**现实中罕见**的情形被大量制造出来。
自检报告的原因分布给出了直接证据：

| 转人工原因 | 3000 样本中触发次数 |
|---|---|
| 手续费超阈值（5000 元） | 1633 |
| 联程票已使用部分航段 | 1114 |
| 已用航段数大于总段数 | 883 |
| 关键信息缺失 | 259 |
| **规则缺口** | **12** |

也就是说：转人工几乎全部来自**转人工条件被高频触发**，而规则覆盖不住的情况只有 12 次。
引擎在这个场景里工作正常——是**数据不代表现实**。

**改法**：暂不改。正确做法不是把转人工条件调松（那是在掩盖问题），
而是给事实字段引入"现实先验"（例如误机率 1%、联程已用 10%），
生成一个分布贴近生产的 `core` 切片，与现在这个以边界覆盖为目的的 `edge` 切片
**分开报指标**。计划在 M4 做。

**复测**：待 M4。在此之前，`eval/README.md` 已明确写明"89.5% 不得当作自动处理率"。

**状态**：已知不修（不修的原因是：这是一个分布建模问题，
不引入先验就无法证明"改完更接近现实"，改了也只是换一个数字）

## 指标与失败模式的关系

失败模式不是收藏品，每条都应该对应一个**可以被自动检测的指标**。填完之后回填这张表：

| 失败模式 | 对应指标 | 测量方法 |
|---|---|---|
| FM-001 | 金额一致率 | 与规则引擎算出的标准答案逐条比对 |
| FM-002 | 同优先级冲突条数（目标 0） | 规则自检报告 + 单元测试 |
| FM-003 | 转人工原因分布（各原因触发频次） | 自检报告的分布表 |
| | | |
