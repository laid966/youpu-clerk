## 2. 设计原则（按优先级）

1. **信任感优先于炫技**：这是给卖家管钱的产品。数字必须醒目、对齐、等宽（`font-variant-numeric: tabular-nums`）；每个价格旁必须能看到"依据"（citation chip）。
2. **一屏一事**：工作台三栏各司其职，不堆装饰。
3. **克制的颜色**：中性灰阶打底，**全产品只有一个强调色**（支付宝蓝，呼应赛事但不过度）；语义色只用于状态（成交=绿、转人工=红、待处理=琥珀）。
4. **过程可见**：trace 时间线（分类→决策→起草→护栏，每步毫秒数）是产品灵魂"钱由程序算"的可视化，要做得像 Stripe 的日志面板一样精致，不要做成 debug 输出。
5. **移动优先但桌面完整**：卖家用手机多；三栏在窄屏折叠为"队列抽屉 + 主区"。

## 5. i18n 规范（面向海外市场，作者明确要求可自由切换）

- 全部 UI 文案走字典：`clerk/web/i18n/zh.js`、`en.js`，`t('key')` 取值；**禁止硬编码文案**。
- 字典 key 按域分组：`nav.*`、`demo.*`、`suggest.*`、`ledger.*`、`report.*`、`pricing.*`、`errors.<CODE>`。
- API 错误的 `code` → 两种语言各有文案（契约 §0）。
- 金额格式：zh `¥379.05`；en `$`? **不**——人民币资产仍显示 `¥379.05`，en 界面写作 `CNY 379.05`；
  将来 eBay 美元商品再引入按币种格式化（`Intl.NumberFormat`），键名预留 `currency`。
- 产品名：zh「有谱掌柜」；en 暂定 **"YouPu Clerk"**（★最终英文名归作者拍板，字典里只有一个 key，改起来一行）。
- **回复话术语言 ≠ UI 语言**：话术跟买家走（契约 §0），UI 跟用户走，界面上要明确标注
  （建议卡角标 `回复语言: EN`），避免店主误解。

## 6. 技术约束

- **零构建**：原生 HTML/CSS/JS（ES modules），FastAPI 静态托管——与 `app/web` 同栈，28 天里构建链是奢侈品。
- 图标：内联 SVG（Lucide 路径手抄即可，不引依赖）。不引前端框架、不引 CSS 框架。
- 可离线开发：`?mock=1` 时前端用内嵌 fixture（直接抄契约 §3 的示例响应）渲染全界面，
  后端未就绪也能开工——**frontend-web 第一周就靠它**。
- 演示模式无需登录：demo 页自动生成临时 `X-Clerk-User`。

- [ ] 所有金额等宽对齐、两位小数？
- [ ] zh/en 切换后无溢出、无漏翻（字典 key 扫描）？
