# 20 · RAG 链路：从"一条 BM25"到"可分级开关的链路"

> 这份文档讲三件事：**这条链路是什么、实测每级值多少、你要填什么。**
>
> 一句话结论：**真正有价值的不是加向量，而是把链路拆成可量化的级——
> 因为第一版就靠这张表抓出了一个"看起来更聪明、实际掉 25 个点"的设计。**

---

## 一、链路长什么样

```
问句
 ↓ ① 查询理解（规则版，确定性、免费）
 │    认指标（"转氨酶"→ alt）+ 认意图（复查/空腹/饮食 → 优先指南层）
 │    ★ 软路由：两层都查，只给优先层加权 —— 不排除任何层
 ↓ ② 召回（BM25；向量那一级还没实现）
 ↓ ③ 融合（RRF，只在有多路时生效：按名次，不是分数相加）
 ↓ ④ 重排（认出的指标 + 优先层加权）
 ↓ ⑤ 拒答判定（最高分低于阈值 → 说"没有依据"，不硬答）
 ↓ ⑥ 回答（受约束：只列命中的依据）
```

命令：

```bat
.\.venv\Scripts\python.exe -m rag stages                  :: 看链路有哪些级、当前怎么配
.\.venv\Scripts\python.exe -m rag trace "尿酸高能不能吃海鲜"  :: 看一条问句走完每一步
.\.venv\Scripts\python.exe -m rag eval --stages           :: 分级增益：每一级值不值
.\.venv\Scripts\python.exe -m rag eval --refusal --sweep  :: 拒答双向 + 阈值取舍曲线
.\.venv\Scripts\python.exe -m rag eval                    :: 基线（单腿 BM25，用于对比）
```

## 二、实测：每一级值多少

36 条用例（31 条模板 + 5 条真实问句），同一套题逐级加开关：

| 级 | Recall@1 | Recall@3 | MRR | ΔRecall@1 |
|---|---|---|---|---|
| ① 基线：只有 BM25 | 91.7% | 97.2% | 0.944 | — |
| ② **+ 软路由 + 指标重排** | **97.2%** | 97.2% | **0.972** | **+5.6%** |
| ③ 反例：硬路由（只查一层） | 72.2% | 72.2% | 0.722 | **-25.0%** |

**第 ③ 行是刻意保留的反例**，不是"更高级的配置"。详见下面。

## 三、两个真实发现（都是这张表逼出来的）

### 发现一：硬路由掉了 25 个点 ★

**第一版我做的就是硬路由**——按关键词判断意图，然后**只查那一层**。

实测：Recall@1 从 91.7% 掉到 **72.2%**。

**根因**：模板问句「ALT 偏高怎么办」里同时有"偏高"（指向解释层）和"怎么办"（指向指南层）。
平局时按名字排序选中了指南层，于是**正确答案所在的解释层被整个排除了**。

**教训（写进代码注释了）**：

> **意图判断天然会错，错的时候不能让它造成不可挽回的损失。**

所以默认改成**软路由**：优先层只在重排时加权（`LAYER_BOOST = 0.2`），
**不排除任何层**。判断错了顶多排序差一点，不会把正确答案删掉。

而硬路由作为 `PipelineFlags(hard_layer_routing=True)` 保留下来，
让这个失败**可以被复现**——`tests/test_rag_pipeline.py` 里有一条测试
断言"软路由永远不差于硬路由"。

> **如果没有那张增益表，我会一直以为硬路由是个好功能。**
> 这就是"每一级都要有自己的数字"这条纪律的直接回报。

### 发现二：拒答阈值**分不开**库内和库外 ★

拒答的双向测量（库内 36 条 / 库外 12 条）：

| 阈值 | 库外被挡住 | 库内被误拒 |
|---|---|---|
| 0.0 ~ 2.9 | 66.7% | **0.0%** |
| 3.8 | 91.7% | 25.0% |
| 6.1 | 100.0% | 55.6% |
| 13.5 | 100.0% | 91.7% |

**要挡住 100% 的库外问题，就得误伤 55%–91% 的库内问题。**

原因是**两个分数分布大幅重叠**：最难的 4 个库外问题拿到了 9–13 分，
和库内正常问题的分数区间一样高。
（例：「孕妇能吃海鲜吗」——知识库有"尿酸与饮食"条目，词几乎全中，但**适用人群不同**。）

**结论：阈值是钝器，靠它解决不了这类难例。**
真正需要的是**"知识库到底覆不覆盖这个话题"**的判断，而不是"分数够不够高"。
这是一个**新的、值得做的级**（见下面第四节）。

## 四、★ 你要填的东西（这就是"边界交给人"的落点）

全部在 **`rag/boundary.py`** —— 那是你的文件。

### ① 拒答边界：`REFUSAL`

| 字段 | 现在的值 | 你要定 |
|---|---|---|
| `min_top_score` | 1.0 | 定多少？**看 `--sweep` 的取舍曲线决定** |
| `min_hits` | 1 | 至少要命中几条才允许开口 |
| `refuse_message` | "知识库中没有找到…" | 拒答时怎么说话 |

**怎么定**：跑 `python -m rag eval --refusal --sweep`，看曲线。
上一节已经告诉你：**光靠阈值分不开**，所以你还得决定
"要不要引入一个'话题覆盖判断'的新机制"。

### ② 什么算"答对"：`CORRECTNESS`

- **严格口径（默认）**：命中的 chunk 必须是标准答案那一条
- **宽松口径**：命中同层任意一条就算对

⚠️ 改成宽松会让分数虚高，**而且和历史基线不可比**。要改请写清理由。

### ③ 意图路由关键词：`INTENT_ROUTING`

哪些问法该优先去哪一层。我给的只是起步词，**按真实问法补**。

### ④ 指标别名：`METRIC_ALIASES`

用户的口语说法 → 指标代码。现在的起步：

```
alt ← 转氨酶 / 谷丙 / gpt
ua  ← 尿酸
crea ← 肌酐
...
```

**每加一个别名，`python -m rag eval` 的分数应该看得见变化。**
如果加了没变化，说明这个别名压根没被用上（有测试守着这件事的原理）。

### ⑤ 拒答问句集：`eval/refusal-questions.jsonl`

我写了 12 条（4 条明显无关 + **8 条"医学相关但知识库没有"的难例**）。
**难例才是真正的考验**——只测"股票明天涨吗"这种，系统不瞎猜就能过。
往里面加你见过的真实边界问题。

## 六、为什么"`audit/` 不许 import `rag/`"

RAG 产出的解读，它的"依据"应该来自知识库的 chunk。
但方向是**调用方把合法引用集合扩大**（传 `extra_citations`），
而不是让审计器去认识知识库。

否则会形成 `audit ↔ rag` 循环依赖——`rag/knowledge.py` 里已经有一个反向的
延迟导入在打这个补丁了。这条边界有 AST 扫源码的测试守着。

## 七、语义腿（Dense）：两条腿都要，但**什么时候要**是有数字的

### 怎么开

```bat
.\.venv\Scripts\python.exe -m rag fetch-model           :: 一次性下载（约 23MB）
.\.venv\Scripts\python.exe -m rag eval --stages --dense :: 语义腿进阶 + 互补性诊断
```

模型：`BAAI/bge-small-zh-v1.5` 的 int8 ONNX（24MB，CPU 即可，**离线零成本**）。
**为什么不用 embedding API**：DeepSeek 没有 embedding 接口（实测 `POST /embeddings` → **404**），
而调第三方 API 会让这一腿**永远进不了 CI**（项目原则：CI 不需要密钥）。
接口是 `DenseBackend` 协议，将来换后端不用改链路。

### 实测：语义腿单独有多强

| 配置 | Recall@1 | MRR |
|---|---|---|
| 只有关键词（BM25） | **91.7%** | 0.944 |
| 只有语义（Dense） | **86.1%** | 0.917 |

### ★ 决定性的那个数字：两条腿的互补性

`rag eval --stages --dense` 会直接给你这张表（**这比 Recall@1 更决定问题**）：

```
两条腿都答对  31 条
只有关键词对   2 条
只有语义对     0 条   ← 语义腿的独有价值
两条都答错     3 条
```

**语义腿一条独占正确都没有。** 它的 86.1% 是关键词腿正确的**子集**——
融合它不会带来新信息，只会稀释。

融合权重扫描（`rag/boundary.py` 的 `FUSION_WEIGHTS`）：

| 语义腿权重 | Recall@1 |
|---|---|
| 0.0 / 0.1 / 0.2 | 97.2%（不亏不赚） |
| 0.3 | 91.7% |
| 0.5 | 88.9% |
| 1.0（等权） | 83.3% |

> **两条腿都要——但现在这条腿还帮不上忙，因为语料只有 15 条。**
> 语料小的时候，用户问的每个指标都有唯一对应的条目，**关键词匹配已经是最优解**。
> 语义腿的价值来自"**同一个问题有多个相近条目**"和"**用户说法与文档用词系统性不同**"——
> 这两种情况在 15 条语料里都还没出现。

**所以语义腿默认关闭，但已经实现、可一键开启、有诊断。**
等你把知识库写大（T11），第一件事就是重跑 `--stages --dense` 看这张互补性表变没变。

### 顺手修掉的一个真 bug

第一版两条腿共用 `index_text()`，语义腿只有 **75.0%**。
根因：`index_text()` 里为 BM25 准备的两样东西对语义模型是**污染**——

- **标题重复两次**：BM25 没有字段权重，重复标题是唯一的加权手段；对语义模型只是稀释正文
- **`keywords` 字段**：每张指标卡都填**同一串**（"偏高 升高 复查 门诊…"），
  让 8 张卡在向量空间里**挤成一团**

拆出 `dense_text()`（只留标题一次 + 正文）后：**75.0% → 86.1%（+11 个点）**。

> **同一条文本服务两种检索器，必然有一边被牺牲。**
> 这条已经写成注释和测试（`test_dense_text_differs_from_index_text`）。

## 八、LLM 两级：改写 与 重排

```bat
.\.venv\Scripts\python.exe -m rag eval --stages --llm   :: **会调模型、会花钱**（重跑走缓存）
```

提示词在你的文件里：**`rag/llm_prompts.py`**（机制在 `rag/llm_stages.py`）。
两条纪律：**解析失败 = 错误**（绝不静默退回）、**必须走缓存**（否则不可复现且重复花钱）。

### 实测

| 级 | Recall@1 | MRR | Δ |
|---|---|---|---|
| ② 软路由 + 指标重排 | 97.2% | 0.972 | — |
| ② + **LLM 查询改写** | **94.4%** | 0.964 | **-2.8%** |
| ② + **LLM 重排** | 97.2% | 0.972 | 无变化 |
| ② + **改写 + 重排** | **100.0%** | **1.000** | **+5.6%** |

### ★ 最微妙的一条：单独有害的级，组合起来是必需的

- **改写单独开：-2.8%**（往问句里加词会稀释 BM25 的精确匹配）
- **重排单独开：无变化**（正确条目根本不在候选窗口里，重排无从下手）
- **两个一起开：100.0%**

因为**改写把正确答案拉进了候选窗口，重排才能选中它**。

> **只测单级增益会得出错误结论**（"改写有害，删掉"）。
> 组合效应只有测组合才看得见——所以评测表里既有单级行也有组合行。

### ⚠️ 这个 100% 能声称多少

**36 条样本全对，只能声称「≥92.0%」**（零失败时 95% 置信下界 = `0.05^(1/36)`）。
要说"召回率 ≥95%"，需要 **59 条**零失败样本；要 ≥99%，需要 **299 条**。

**所以下一步不是庆祝 100%，而是把评测集做大**——这也正好是 T3 和 T11 的活。

## 九、你的问题：知识库能不能用别人开源的？

**能，但有三个前提条件，而且"文件更多"不会自动提高正确率。**

### 前提一：许可必须干净

这个项目是公开作品集，面试官会问"你的知识库哪来的、有授权吗"。

| 可以 | 不建议 |
|---|---|
| 政府公开数据（如国家药监局公开的说明书信息） | 中华医学会临床指南（有版权） |
| 维基百科/维基医学（CC BY-SA，**要标注来源**） | 丁香园、医脉通等商业内容 |
| 美国 NLM 的 MedlinePlus / MedQuAD（英文，公有领域） | 直接扒别人网站 |
| 你**自己改写**的通俗解释（现在这条路） | 把受版权保护的指南原文入库 |

**建议**：**选明确开放许可的来源，并在知识库里逐条标注出处**——
"可以溯源"本身就是这个项目的卖点。

### 前提二：必须和判定域规则对齐（这条最容易被忽略）

审计器做**引用存在性检查**：解读里出现的依据必须在一个"合法引用集合"里。
这个集合 = 判定域规则的 `cite` + 知识库的 chunk id（`extra_citations`）。

**外部知识库直接 dump 进来，它的引用格式跟你的域规则对不上**——
结果是**每一条引用都被判为"编造"**，整个审计层全是误报。

所以外部内容必须**加工成你的 chunk 结构**（`rag/knowledge.py` 的 `Chunk`），
而不是原样丢进去。

### 前提三：评测集必须同步扩大，否则数字不可信

现在是 **36 条问句 / 15 条 chunk**。如果把知识库扩到 1000 条而评测集还是 36 条：

- 更替后的 36 条是否还有代表性？**没人知道**
- 分母太小，分数会剧烈抖动

**扩容必须和评测集扩容一起做**，否则你拿到的分数没有意义。

### ★ 最关键的一条："更多文件"很可能会先**降低**正确率

这在检索里叫**稀释（dilution）**：候选条目变多，同一个词（"偏高""复查"）会匹配到更多无关条目，
而 BM25 的 IDF 会因此改变——**准确率先掉，而不是先升**。

**而这个项目的评测框架正好能把它量出来。** 具体做法（T11）：

1. 先把现在 15 条 chunk 的成绩记下来（**91.7% / 97.2%**）
2. 分批扩容（比如 15 → 50 → 200 → 1000），**每批都重跑 `rag eval --stages --dense`**
3. 看两条曲线：
   - **关键词腿**的 Recall@1 会先掉（稀释）
   - **语义腿**的独占正确数会从 0 开始上升（终于有相近条目了）
4. 找到那个**语义腿开始有价值**的规模——**那才是"加向量"有据可依的时刻**

> **扩容不是免费的午餐**：它同时带来"覆盖面"和"稀释"，
> 而这两者的净值**只有测出来才知道**。
