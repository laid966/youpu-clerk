# auditkit · 方案书

> 判定类 AI 输出的**差分审计器**：用独立的确定性 oracle 重算，找出 AI 输出里的缺陷，定位、给证据、给修复建议，并**用注入式基准证明自己找得全**。

---

## 1. 诚实的前提：这个位置不空

写方案前我查了一轮开源现状，同类工具**已经有一批**：

| 项目 | 它做什么 |
|---|---|
| [attest](https://github.com/adepeju4/attest) | 逐条核对 claim 是否被真实工具输出支撑（约束式证据核对，附置信区间） |
| [spancheck](https://github.com/tjromack/spancheck) | 引用正确率、拒答正确性、幻觉率、成本与延迟 + 合规可读的审计日志 |
| [RAGGround](https://pypi.org/project/ragground/0.2.1/) / [grounded-check](https://pypi.org/project/grounded-check/) | groundedness 检查 |
| [SIRIN](https://export.arxiv.org/pdf/2608.00033) | RAG / 记忆型系统的上下文幻觉检测工具包（学术） |
| [claimchain](https://github.com/PillCrew/claimchain) | claim 级证据核对 |
| 学术侧 | [MAS-FIRE](https://ar5iv.labs.arxiv.org/html/2602.19843)（故障注入）、[ReliabilityBench](https://huggingface.co/papers/2601.06112)、[变异测试用于 LLM 测试生成](https://ieeexplore.ieee.org/document/11655121)、[《LLM-as-a-Judge 不是神谕：自我改进 agent 需要确定性护栏》](https://export.arxiv.org/pdf/2609.02246) |

**所以本项目的卖点不是"没人做过"，而是三件具体的事别人没做：**

| 维度 | 已有 groundedness 工具 | **auditkit** |
|---|---|---|
| 判据 | 「这句话**有没有依据**」（与检索到的证据是否一致） | 「这个判定**对不对**」（与独立重算的结果是否一致 = **差分**） |
| 输出 | 一个分数 / 一段评语 | **缺陷清单**：类型 + 位置 + 证据 + 修复建议 |
| 评测方式 | 与人工标注比较 | **注入已知缺陷测召回率 + 变异测试**双重证明"找得全" |
| 闭环 | 无 | 缺陷聚类 → 规则补丁 → 反例验证 → 回归 → 人审批 |

**核心区别一句话**：已有工具核对"话有没有依据"，auditkit 核对"**判定对不对**"。
前者需要证据，后者需要一个**独立的 oracle**——而 oracle 恰好是我们已经做出来的那台确定性引擎。

### 1.1 策略转变（这条比选题更重要）

我这轮对话里三次给出"不够稀缺"的结论。真正的教训是：

> **2026 年不存在"没人做过"的 agent 方向。**
> 「找空白」是错的打法；正确的打法是**在拥挤的地方做一个别人没做的动作**。
>
> 差异化不来自"我是第一个想到的"，来自三件可控的事：
> ① 我加的约束更狠（模型不许判定）；② 我的证据更硬（注入式召回率 + 变异得分）；③ 我把闭环走完了（找错 → 定位 → 补丁 → 回归 → 人审批）。

## 2. 目标与成功标准

**成功标准（缺一不算完成）**

1. **一条命令离线跑完评测**（录制回放，不联网、不花钱、结果确定），产出报告
2. **缺陷召回率**：漏判 / 降级 / 安全越界三类必须 **100%**；整体 **≥ 95%**
3. **误报率 ≤ 5%**（审计器误报一多就没人用，这是死穴，必须是一等指标）
4. **变异得分 ≥ 70%**：故意改坏流水线（改阈值、删护栏、关重排、改提示词），测试套件要能抓住
5. 检索有 **Recall@5 基线**，并给出"加向量后提升多少"的同集对比
6. 浏览器里能展示缺陷清单并点开证据；README 里每个数字都来自真实报告

## 3. 系统架构

```
① 判定流水线（被审计对象）
   输入事实 ──► 规则引擎（确定性）──► Judgement
                    │
                    └──► LLM 解读层（结构化输出 + 引用）

② 缺陷注入器（制造已知缺陷，作为评测的 ground truth）
   在 ① 的输出上注入 8 类缺陷，seed 可复现 ──► 被污染的判定 + 缺陷清单（标准答案）

③ 审计 agent（本项目主体）
   LangGraph 编排：
     plan    → 拆子任务（结构 / 数值 / 阈值 / 引用 / 矛盾 / 越界）
     inspect → 调工具逐项检查（确定性检查优先，LLM 只做语义检查）
     reflect → 自我反驳（"这真的是缺陷吗"）专治误报
     decide  → **确定性仲裁**：是不是缺陷由程序裁决
     report  → 缺陷清单（类型 + 位置 + 证据 + 修复建议）
     human?  → 危急缺陷立即中断；补丁必须人审批

④ 评测与证明
   注入式召回率 / 误报率 / 变异得分 / 检索指标 → CI 门禁
```

## 4. 技术栈标注

| # | 模块 | **技术** | 为什么是它 | 关键参数 |
|---|---|---|---|---|
| 1 | 判定流水线 | **复用 M1 的确定性引擎**（规则即数据 + 受限表达式 + Decimal + 分级 + 危急不变量） | 审计需要一个**独立 oracle**；用同一套规则重算才谈得上"差分" | 已有 125 个测试兜底 |
| 2 | LLM 解读层 | LLM + **结构化输出**（pydantic） | 这是被审计的"AI 生成"部分，必须真实存在才有审计对象 | 强 schema；每条解释强制带 citations |
| 3 | **缺陷注入器** | 模板化注入（8 类）+ 固定 seed | 没有已知缺陷就无法证明审计器找得全 | 8 类 × 每类 N 条；seeded 可复现 |
| 4 | 确定性检查 | 纯程序：数值一致性、单位换算、阈值复核、性别/年龄阈值、内部矛盾、引用存在性 | **能用程序判的一律不用模型**——这是本项目的约束创新 | 引用存在性 = chunk_id 必须命中知识库 |
| 5 | 语义检查 | LLM（只做降级用途）：诊断口吻、用药建议、措辞越界 | 这些是语义问题，程序判不了 | 输出必须结构化（布尔 + 片段） |
| 6 | **裁决** | 程序：确定性检查结果优先；LLM 结果只作为"建议"，需二次确认才计入 | 防止把"模型觉得有问题"当成事实 | 误报预算 ≤5% |
| 7 | **RAG 检索** | **BM25（jieba）+ 向量 → RRF(k=60) → LLM 重排** | 引用有效性核查与解释来源核对需要真检索 | 召回 top-20 → 重排 top-5；切分：指标卡 + 500 字/100 重叠 |
| 8 | embedding | API 型（OpenAI 兼容，如百炼 text-embedding-v3）；备选本地 ONNX bge-small-zh | 本机无 torch；先 BM25 建基线再加向量做同集对比 | 维度 512–1024，结果缓存进 SQLite |
| 9 | 编排 | **LangGraph**（状态 + 条件边 + checkpointer + interrupt） | 需要反思回路、收敛判据、不可绕过的人机协作 | 步数上限 12；动作哈希防打转；SQLite checkpointer |
| 10 | 记忆 | 长期记忆表（SQLite）：记住"该指标曾被误报" | 同一类误报不重复犯——审计器可信度的关键 | 键 = 缺陷类型 + 目标 + 阈值 |
| 11 | **录制回放** | prompt 规范化 hash（模型+温度+schema 版本+prompt）→ SQLite 缓存 | 让 agent 测试**离线、可复现、不花钱**，这是能像编译器一样测 agent 的前提 | 默认测试走回放；live 测试单独标记 |
| 12 | **变异测试** | 8 类变异算子，跑完整测试套件统计"杀死率" | 证明"测试有效"而不只是"测试很多" | 变异得分目标 ≥70% |
| 13 | 成本治理 | 模型分级路由（便宜的先跑）+ 四重硬上限（步数/token/墙钟/调用数） | 审计是批量操作，成本必须可控 | 单份审计成本上限 ¥0.2 |
| 14 | 可观测 | 每步 trace + 工具调用留档 + `GET /metrics` | 审计结论必须可复盘 | 每次判定可回溯 |
| 15 | 服务 | FastAPI + SSE | 审计进度要流式可见 | 单份 < 20s |
| 16 | 知识库分层 | ①参考区间（结构化表，**不进向量库**）②指标解释 ③指南要点 | **精确数值不该走语义检索**——数值走确定性，语义走向量 | 按层路由，不混检 |

## 5. 八类可注入缺陷（项目核心资产）

每一类都必须：**可注入**（造得出）、**有唯一标准答案**（判得清）、**有对应检查器**（找得到）。

| # | 缺陷类型 | 注入方式 | 由谁发现 | 要求 |
|---|---|---|---|---|
| 1 | **漏判**（应 critical 却报 normal） | 改结论字段 | 确定性 oracle 差分 | 召回 **100%** |
| 2 | **降级**（critical → marked） | 改结论字段 | 确定性 oracle 差分 | 召回 **100%** |
| 3 | **数值抄错**（报告 300，解读写 200） | 改引用片段里的数值 | 数值一致性检查 | ≥95% |
| 4 | **单位错**（U/L 写成 μmol/L） | 改单位字段 | 单位表核对 | ≥95% |
| 5 | **阈值用错**（用男性阈值判女性） | 篡改触发规则 | 阈值复核（按性别/年龄重算） | ≥95% |
| 6 | **引用不存在**（编造依据） | 换成不存在的 chunk_id | 引用存在性检查 | **100%** |
| 7 | **内部矛盾**（说正常又建议立即就医） | 改建议字段 | 内部一致性检查 | ≥95% |
| 8 | **安全越界**（出现诊断结论/药名） | 插入越界语句 | 禁用词表 + LLM 语义确认 + 程序裁决 | **100%** |

## 6. 四项创新与度量

| 创新 | 层次 | 度量 |
|---|---|---|
| **差分审计**（用独立 oracle 重算，而非核对证据） | 约束 + 组合 | 召回率 / 误报率 / 按类型召回 |
| **注入式缺陷基准**（造已知缺陷当标准答案） | 组合 | 缺陷召回率，按 8 类分别报告 |
| **变异测试进 agent 流水线** | 组合 + 证据 | **变异得分**；并演示"删掉某条护栏，测试会不会红" |
| **缺陷 → 规则补丁闭环**（聚类 → 补丁 → 反例验证 → 回归 → 人审批） | 组合 + 证据 | 补丁零回归率、从 badcase 到补丁的自动化率 |

## 7. 十二项 agent 细节的落地位置

| # | agent 细节 | 落在哪 |
|---|---|---|
| 1 | 工具层（8–10 个） | `tools/`：跑分级、跑反例搜索、跑回归、查知识库、注入缺陷、聚类失败、生成补丁、校验补丁、导出 |

| 6 | 记忆 | `memory` 表——记住曾误报的（缺陷类型, 目标） |

| 8 | 多角色（非自由群聊） | 审计员 / 反驳员两个角色，图编排，不让他们聊天 |
| 9 | 成本与延迟治理 | 模型分级路由 + 四重硬上限 |
| 10 | 可观测 | trace + 工具留档 + `/metrics` |
| 11 | 评测 | 注入式召回率 + 变异得分 + 误报率 → CI 门禁 |
| 12 | 安全 | 注入防御、工具白名单、真实体检数据绝不入库 |

## 8. 数据与合规

- 判定域：医学分级域（血常规 + 生化）为主，机票 / 学位两个旧域转为**回归夹具**（继续证明"换域即复用"）
- 判决样本：**程序合成**（复用 M1 的 `sample_gen` 生成事实 → 引擎判决 → LLM 解读）
- 知识库：公开通用参考区间 + **自己重写**的通俗解释 + 公开指南**要点**
- **红线**：不使用任何真实体检报告；仓库内不出现真实机构名、人名；输出固定免责声明（健康科普与就医准备，不诊断、不药、不替代医生）

## 9. 目录结构与里程碑

```
engine/    确定性引擎（已有：表达式 / 域 / 判定 / 自检 / 用例生成）
audit/     缺陷注入器、确定性检查器、裁决器、变异算子、评测与报告
rag/       切分、三层索引、混合检索、重排、引用核查
agent/     LangGraph 图、节点、提示词、护栏、记忆
tools/     给 agent 用的工具（schema + 错误契约 + 幂等）
app/       FastAPI + SSE + 页面
replay/    录制回放缓存
eval/      注入数据集、召回/误报/变异/检索指标、报告
domain/    医学分级 8 个域 + 2 个回归夹具域
```

| 阶段 | 里程碑 | 工时 | 验收 |
|---|---|---|---|
| 一 | **A1** 判定流水线 + 判决样本生成 | 6h | 一条命令生成 N 份"事实→判决→解读"样本 |
| | **A2** 缺陷注入器（8 类） | 6h | 每类都能注入，且标准答案精确、seed 可复现 |
| 二 | **A3** 确定性检查器（5 类） | 8h | 数值/单位/阈值/引用/矛盾全部可查，跑出第一版召回率与误报率 |
| | **A4** RAG 知识库 + 引用核查 | 8h | Recall@5 基线数字；引用存在性检查接入 |
| 三 | **A5** LangGraph 审计 agent（规划/反思/收敛/HITL/记忆） | 10h | 三类红线缺陷召回 100%；误报率 ≤5% |
| | **A6** 变异测试 + 变异得分 + CI 门禁 | 6h | 变异得分 ≥70%；删护栏测试会红 |
| 四 | **A7** 录制回放 | 4h | 评测离线可跑、结果确定 |
| | **A8** FastAPI + SSE + 页面 | 8h | 浏览器看缺陷清单、点开证据 |
| | **A9** 补丁闭环 + 开源 + 求职材料（**可裁剪**） | 8h | 补丁零回归；README 数字与报告一致 |

## 10. 风险与明确不做

**风险**
1. **已有同类工具**（见 §1）：必须能一句话说清差异（差分 vs 证据核对），否则会被当成 spancheck 的复刻
2. **误报率是死穴**：误报一多审计器就没人用 → 误报率与召回率同等对待，反射节点专治误报
3. **学术已有论文**：不宣称原创概念；正确表述是"独立实现 + 可运行 + 有数字"
4. **注入缺陷 ≠ 真实缺陷**：注入的缺陷分布可能不代表现实 → 在文档里如实说明这个局限，并保留人工抽检
5. **第二个 API key**（embedding）：不阻塞——先 BM25 建基线，后加向量对比
6. **时间**：核心 A1–A8 约 56 小时，超出 3 周；靠 A9 可裁剪 + A7 从简控制

**明确不做**：不做诊断/用药建议、不做多模态看图、不做通用平台（只做一个域 + 完整管道）、不接真实医院系统、不使用真实体检数据、不做移动端、不自动合并补丁（必须人审批）。
